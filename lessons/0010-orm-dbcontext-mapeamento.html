Lição 10 — Back-End

ORM, DbContext, Change Tracker e Mapeamento

Como o Entity Framework Core traduz objetos C# em tabelas SQL, gerencia estados e evita bugs de concorrência.

🧱 Impedância Objeto-Relacional e ORM

Object-Relational Impedance Mismatch é a diferença estrutural entre dois mundos:

  • Objetos (C# / Java): têm referências, herança, listas e comportamento.
  • Banco Relacional (SQL): tem tabelas, linhas, colunas, chaves (PK/FK) e joins.

O ORM (Entity Framework Core no C#, equivalente ao Hibernate/JPA no Java) faz o mapeamento automático (Classe ↔ Tabela, Propriedade ↔ Coluna, Objeto ↔ Linha) e gera o CRUD em SQL.

⏱️ DbContext: Scoped vs Singleton

O AppDbContext representa uma sessão curta de trabalho com o banco e expõe DbSet<T> para cada tabela. No ASP.NET Core, AddDbContext o registra como Scoped por padrão:

Ciclo de VidaComportamentoUso com DbContext
Scoped1 instância nova por requisição HTTP; descartada ao terminar✅ Obrigatório / Padrão
Singleton1 única instância para toda a aplicação (todas as requisições)❌ Proibido!
⚠️ Por que NUNCA usar DbContext como Singleton?
  • Não é thread-safe: duas requisições simultâneas acessando o mesmo contexto causam erros de concorrência.
  • Vazamento de memória: entidades ficam presas no rastreamento indefinidamente.

🕵️ Change Tracker: como o SaveChanges sabe o que fazer

O Change Tracker é o "fiscal" dentro do DbContext. Ele acompanha cada entidade pelo seu estado e, quando você chama SaveChangesAsync(), gera o SQL exato:

EstadoQuando aconteceSQL gerado no SaveChanges
DetachedNão rastreada (ex.: AsNoTracking())Nenhum
UnchangedCarregada do banco e não alteradaNenhum
AddedMarcada com db.Products.Add(p)INSERT (+ preenche Id)
ModifiedPropriedade alterada em entidade rastreadaUPDATE (só colunas alteradas)
DeletedMarcada com db.Products.Remove(p)DELETE

🗺️ Mapeamento (Data Annotations vs Fluent API) e 1:N

  • Convenções: regras automáticas (Id → PK; CategoryId → FK).
  • Data Annotations ([Required], [Range]): recomendadas em DTOs para validar entrada HTTP.
  • Fluent API (no OnModelCreating): recomendada para regras estruturais do banco (HasMaxLength, HasIndex().IsUnique(), HasPrecision, HasOne/WithMany, OnDelete).

No relacionamento 1:N (Category 1 → N Product), usar .OnDelete(DeleteBehavior.Restrict) impede excluir uma categoria que ainda tenha produtos vinculados (diferente de Cascade, que apagaria os produtos junto).

🧪 Teste rápido

1. Por que o DbContext NÃO deve ser registrado como Singleton em uma Web API?

  • Causa erros de concorrência e memória
  • Impede o uso de SQLite local
  • Bloqueia a criação de novas migrations
  • Desativa automaticamente todas as chaves estrangeiras
✅ Isso! O DbContext não é thread-safe (concorrência entre threads) e acumula entidades rastreadas na memória.
❌ Lembre-se: DbContext foi feito para vida curta (Scoped). Em Singleton, várias threads competem e ele vaza memória.

2. Uma entidade buscada normalmente no banco teve seu preço alterado. Qual estado ela assume?

  • Modified para gerar comando UPDATE
  • Added para gerar comando INSERT
  • Detached para ignorar o banco
  • Unchanged para pular o SaveChanges
✅ Perfeito! Consultas rastreadas entram como Unchanged e passam para Modified ao alterar uma propriedade.
❌ Atenção: entidade buscada e alterada vira Modified, fazendo o SaveChangesAsync gerar um UPDATE.

3. O que acontece com DeleteBehavior.Restrict ao tentar apagar uma Category com Products?

  • Bloqueia a exclusão por erro de FK
  • Apaga todos os produtos em cascata
  • Define o campo CategoryId como nulo
  • Move os produtos para outra categoria
✅ Exato! Restrict protege a integridade referencial e impede a exclusão enquanto houver filhos vinculados.
❌ Quem apaga os filhos junto é o Cascade. O Restrict bloqueia a exclusão por violação de chave estrangeira.
