Lição 11 — Back-End

LINQ, AsNoTracking, N+1, Migrations e Transações

Como evitar consultas lentas, versionar o banco com segurança e garantir atomicidade no EF Core.

⚡ IQueryable: filtre no banco, não na memória

Enquanto a consulta é IQueryable, o EF Core ainda está montando o SQL. Só quando você chama ToListAsync(), FirstAsync() ou SingleOrDefaultAsync() ela é materializada (executada no banco):

// ✅ EFICIENTE: Where roda no SQL (SELECT ... WHERE Price >= @minPrice)
var result = await db.Products
    .AsNoTracking()
    .Where(p => p.Price >= minPrice)
    .Select(p => new ProductResponse(p.Id, p.Name, p.Price))
    .ToListAsync(ct);

// ❌ INEFICIENTE: traz a tabela inteira para a memória e filtra em C#
var todos = await db.Products.ToListAsync(ct);
var baratos = todos.Where(p => p.Price < 10);
  • AsNoTracking(): desativa o Change Tracker em consultas somente leitura (GET), economizando memória e CPU. Não use em PUT ou DELETE, pois você precisa do rastreamento para o SaveChangesAsync().
  • Select(...) (Projeção): traz apenas as colunas necessárias para o DTO, evitando overfetching.

🔁 O problema N+1 (Lazy vs Eager vs Projeção)

EstratégiaComo funcionaConsultas SQL (para 50 pedidos)
Lazy LoadingCarrega pedido.Cliente sob demanda dentro do foreach❌ 1 + 50 = 51 consultas (N+1)
Eager LoadingUsa .Include(p => p.Cliente) para trazer junto✅ 1 consulta (JOIN)
ProjeçãoUsa .Select(p => new Dto(...)) direto para DTO✅ 1 consulta enxuta (preferida em APIs)

📦 Migrations: versionamento do schema

  • dotnet ef migrations add InitialCreate → compara as classes/Fluent API com o snapshot e gera código com Up() (aplicar) e Down() (desfazer).
  • dotnet ef database update → executa as migrations pendentes no banco.
  • __EFMigrationsHistory: tabela automática no banco que registra quais migrations já foram aplicadas.

🔒 Transações: Implícita vs Explícita

  • Implícita (SaveChangesAsync() único): o EF Core já executa todos os comandos daquele único SaveChangesAsync dentro de uma transação automática.
  • Explícita (BeginTransactionAsync()): necessária quando você tem múltiplos SaveChangesAsync() que precisam de atomicidade (ou tudo dá CommitAsync(), ou tudo sofre RollbackAsync() em caso de erro — ex.: atualizar estoque + registrar StockMovement).

🧪 Teste rápido

1. Ao buscar 50 pedidos e acessar pedido.Cliente.Nome no foreach com Lazy Loading, quantas queries rodam?

  • 51 consultas (1 inicial mais 50)
  • 50 consultas (uma para cada cliente)
  • 2 consultas (pedidos e depois clientes)
  • 1 consulta (com JOIN automático)
✅ Isso! 1 consulta para os 50 pedidos + 50 consultas dentro do loop = 51 (problema N+1).
❌ Atenção: além das 50 consultas do loop, houve a 1ª consulta para buscar os pedidos (1 + N = 51).

2. Quando o uso de AsNoTracking() traz ganho real sem quebrar a operação?

  • Em consultas GET somente para leitura
  • Em endpoints PUT para alterar preços
  • Em endpoints DELETE para remover linhas
  • Em transações explícitas com dois saves
✅ Exato! Leituras não precisam de Change Tracker; PUT e DELETE precisam do rastreamento para SaveChangesAsync.
❌ Lembre-se: PUT e DELETE precisam que o Change Tracker rastreie a entidade. Use AsNoTracking apenas em leituras.

3. O que a tabela __EFMigrationsHistory armazena no banco de dados?

  • As migrations já aplicadas no banco
  • O histórico de alterações de estoque
  • As entidades rastreadas pelo Change Tracker
  • Os logs de exceções da aplicação
✅ Perfeito! Ela registra quais migrations já foram aplicadas para o EF Core saber o que falta rodar.
❌ Não! A tabela __EFMigrationsHistory controla exclusivamente o histórico de migrations aplicadas no schema.
