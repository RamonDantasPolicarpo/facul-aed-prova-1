Lição 12 — Back-End

DTOs, Validação, ProblemDetails e Padrões

Como blindar o contrato da API, padronizar erros HTTP e entender DAO, Repository e Unit of Work.

🛡️ Por que usar DTOs em vez de Entidades?

Nunca receba nem devolva entidades do EF Core diretamente nos endpoints. Use DTOs (CreateProductRequest, ProductResponse):

  • Evita ciclos de JSON: Category aponta para Products, que aponta para Category (loop infinito na serialização).
  • Segurança / Overposting: impede que o cliente envie campos que não deveria (como Id).
  • Evita Overfetching: trafega só o necessário.
  • Desacoplamento: você pode mudar a tabela sem quebrar o contrato HTTP.

🏛️ DAO, Repository e Unit of Work

PadrãoPapelNo EF Core
DAOEncapsula acesso SQL direto ao banco(Abstraído pelo ORM)
RepositoryAbstrai acesso a dados como coleçãoDbSet<T> (db.Products)
Unit of WorkCoordena alterações em lote e transaçãoDbContext + SaveChangesAsync()
💡 Dica do slide 42: Não crie GenericRepository<T> por reflexo! O DbContext já oferece Repository + Unit of Work. Só crie repositórios específicos quando precisar encapsular consultas de domínio complexas.

🧪 Teste rápido

1. Qual problema de serialização ocorre ao retornar entidades com navegação bidirecional sem DTO?

  • Ciclo infinito ao serializar JSON
  • Erro de sintaxe nas migrations
  • Desativação automática do Change Tracker
  • Conversão de POST para GET
✅ Isso! Category → Products → Category gera ciclo infinito no JSON. DTOs resolvem isso.
❌ Lembre-se: navegações bidirecionais (Category ↔ Product) causam ciclo infinito na serialização JSON.

2. No GlobalExceptionHandler, qual status HTTP é retornado para uma DbUpdateException (conflito de banco)?

  • 409 Conflict com ProblemDetails
  • 204 No Content sem corpo
  • 401 Unauthorized sem token
  • 201 Created com novo Id
✅ Exato! Conflitos de persistência (como FK ou índice único) viram 409 Conflict; erros genéricos viram 500.
❌ Atenção: DbUpdateException é um conflito de persistência, mapeado para 409 Conflict.

3. Por que o slide recomenda não criar GenericRepository<T> por reflexo sobre o EF Core?

  • DbContext já atua como UoW
  • EF Core proíbe interfaces genéricas
  • SQLite não suporta padrão Repository
  • GenericRepository bloqueia uso de DTOs
✅ Perfeito! DbSet<T> já funciona como Repository e DbContext como Unit of Work; encapsular demais esconde o LINQ.
❌ Não! O motivo é que DbContext + DbSet já oferecem comportamento de Unit of Work e Repository.
